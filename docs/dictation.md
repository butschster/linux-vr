# Голосовое управление и ввод текста

Зажал кнопку на контроллере — сказал — отпустил. Дальше одно из двух:
текст появился там, где фокус, или выполнилось действие.

Триггер на контроллере, а не на клавиатуре: цель — управлять голосом,
руки при этом свободны и на клавиатуре не лежат.

## Два режима, и почему их надо различать явно

| Режим | Что говоришь | Что происходит |
|---|---|---|
| **Диктовка** | «привет, как дела» | текст вставляется в текущий фокус |
| **Команда** | «переключи окно» | выполняется действие |

Соблазн сделать один режим и угадывать намерение по содержанию — ловушка.
Ошибка классификации в одну сторону вставляет в документ слово «переключи окно»,
в другую — молча съедает продиктованную фразу. Оба случая раздражают
непредсказуемостью.

**Решение: разные кнопки.** Триггер — курок, команда — кнопка A (или наоборот).
Детерминированно, объяснимо, не требует ни модели-классификатора, ни доверия к ней.

## Схема

```
Quest (наш клиент)                       Ubuntu (хост-агент)
  кнопка зажата
     │
  AAudio, 16 кГц моно PCM
     │
     └──── PCM + тег режима ───────────►  буфер
  кнопка отпущена                            │
     └──── маркер конца ──────────────►      ▼
                                        Whisper (API или локально)
                                             │ текст
                              ┌──────────────┴──────────────┐
                              ▼                             ▼
                        режим ДИКТОВКА                режим КОМАНДА
                              │                             │
                     сохранить буфер обмена         разбор во фразу
                     wl-copy «текст»                        │
                     uinput: Ctrl+V                  последовательность
                     вернуть буфер обмена              скан-кодов
                              │                             │
                              ▼                             ▼
                     текст в фокусе                  действие выполнено
```

Триггер целиком на стороне клиента: OpenXR actions, никакого перехвата хоткеев
на хосте и никакого обратного канала «начни запись». Хост только принимает аудио.

## Засада: GNOME Wayland не отдаёт управление окнами

Это главное, что определяет реализацию командного режима.

Под X11 внешняя программа могла перечислить окна и переключиться на нужное
(`wmctrl`, `xdotool`). **Под Wayland с mutter такого API нет.** Приложение не может
ни узнать список окон, ни сфокусировать чужое. Это не недоработка, а модель
безопасности Wayland. Обходы — расширение GNOME Shell со своим D-Bus-интерфейсом,
то есть отдельный компонент, который ломается на каждом обновлении GNOME.

**Поэтому команды выражаем клавиатурными сочетаниями, а не вызовами API.**
Их `uinput` отправляет без всяких разрешений, и они работают ровно так же,
как если бы человек нажал их сам:

| Фраза | Что отправляем |
|---|---|
| «переключи окно» | `Alt+Tab` |
| «закрой окно» | `Alt+F4` |
| «второй рабочий стол» | `Super+2` |
| «открой терминал» | `Ctrl+Alt+T` |
| «поиск» | `Super`, затем текст |
| «скопируй» / «вставь» | `Ctrl+C` / `Ctrl+V` |

Это не компромисс: клавиатурные сочетания — единственный интерфейс, который
на GNOME Wayland доступен снаружи и не зависит от версии оболочки.

## Засада: текст нельзя набирать посимвольно

Для режима диктовки.

`uinput` работает **скан-кодами, привязанными к раскладке**. Кириллица, знаки
препинания, любой не-ASCII — превращаются в мусор или зависят от того, какая
раскладка активна в момент вставки. Пользователь переключил язык — вывод сломался.

`wtype` не спасает: он использует протокол `zwp_virtual_keyboard`, который
**mutter не реализует**. На GNOME Wayland это тупик.

**Буфер обмена не зависит ни от раскладки, ни от протокола ввода.** `wl-copy`
кладёт готовый UTF-8, `Ctrl+V` — два скан-кода, одинаковых в любой раскладке.

Обязательное условие: **сохранять и возвращать предыдущее содержимое буфера.**
Иначе диктовка молча затирает то, что человек скопировал минуту назад — поведение,
которое бесит и не сразу диагностируется.

## Разбор команд

Начинать с простого сопоставления фраз по словарю. Whisper выдаёт достаточно
стабильный текст, чтобы это работало, а поведение остаётся предсказуемым:
не распозналось — ничего не произошло, и это лучше, чем сделать не то.

Языковую модель для разбора подключать только если словаря окажется мало.
У неё своя цена: задержка, стоимость и главное — недетерминированность там,
где нужна ровно обратная.

Отдельно: **команда должна подтверждаться**. Голос ошибается чаще клавиатуры,
и «закрой окно» по ослышке — потерянная работа. Минимум: показывать распознанную
фразу в углу слоя перед выполнением, деструктивные действия — с подтверждением.

## Где крутить Whisper

Внешний OpenAI API не нужен: **используем self-hosted Whisper на GPU.**

Схема — `whisper-large-v3-turbo` (faster-whisper CT2) за OpenAI-совместимым
гейтвеем. Эндпоинт стандартный: `POST /v1/audio/transcriptions`, модель
занимает около 3 ГБ VRAM.

Адрес гейтвея и ключ берутся из переменных окружения:

```sh
LINUXVR_ASR_URL=http://<гейтвей>:4000/v1/audio/transcriptions
LINUXVR_ASR_KEY=<ключ>
LINUXVR_ASR_MODEL=whisper-large-v3-turbo
```

Что это даёт:

- **Модель уровня large-v3-turbo**, а не компромиссная маленькая.
- **Ноль стоимости за минуту** — железо своё.
- **Аудио не уходит наружу.**
- **Клиентский код тот же**, что для OpenAI — API совместим.

### Ограничение, которое пока сознательно принимаем

Гейтвей доступен **только через VPN**. С хоста VR-десктопа маршрут идёт через
туннель, замеренный **RTT — 74 мс**. Плюс инференс и передача.

**Для концепта это неважно** — задержка в районе секунды устраивает, а один путь
вместо двух означает вдвое меньше кода и ни одной развилки в отладке.

Что откладываем осознанно, чтобы потом не удивляться:

- **Задержка команд.** Команда из двух слов, срабатывающая через секунду,
  в ежедневном использовании ощущается как «не сработало», и человек жмёт
  кнопку второй раз. Когда концепт заработает — мерить и решать.
- **Зависимость от туннеля.** Упал VPN — отвалилось голосовое управление.
  Для инструмента на каждый день это плохая зависимость.

Оба лечатся одним и тем же: локальный `whisper.cpp` как вторая реализация
за тем же интерфейсом. На Ryzen 7 6800U с 16 потоками модель `small` считает
короткую фразу быстрее реального времени. **Поэтому интерфейс распознавания
делаем сменным с самого начала** — это единственное, что стоит заложить сейчас
ради будущего, потому что переделывать потом дороже, чем предусмотреть сразу.

### Предобработка аудио не нужна

Готовые сайдкары для подготовки аудио (нормализация в 16 кГц моно Opus,
нарезка длинных записей по тишине) решают задачу часовых записей,
не влезающих в один запрос.

У нас push-to-talk на несколько секунд: клиент и так пишет 16 кГц моно —
ровно то, что нужно Whisper. Ни транскодирование, ни нарезка не требуются.

Ключ гейтвея — только из переменной окружения. В конфиг и в репозиторий
он не попадает никогда.

## Что нужно на стороне клиента

- OpenXR actions на кнопки контроллера — две отдельные, по режиму на каждую.
- Разрешение `android.permission.RECORD_AUDIO`. Для `NativeActivity` запрос
  runtime-разрешения делается через JNI — отдельная небольшая возня.
- Захват через **AAudio**, 16 кГц моно PCM — ровно то, что ест Whisper,
  без пересэмплирования.
- Индикация в слое: идёт запись, что распозналось. Без обратной связи
  голосовой интерфейс ощущается сломанным, даже когда работает.

## Что нужно на стороне хоста

- Демон: принимает аудио, распознаёт, исполняет.
- `wl-clipboard` для буфера обмена, `uinput` для скан-кодов — оба доступны,
  пользователь уже в группе `input`.

## Порядок реализации

Делать после вехи C, когда есть рабочий стрим и управляющий канал.

1. Хост-агент: распознавание файла-заглушки → вставка через буфер обмена.
   Проверяется без гарнитуры.
2. Словарь команд → скан-коды. Тоже без гарнитуры.
3. Клиент: разрешение, AAudio, кнопки, отправка PCM.
4. Соединить, померить задержку от отпускания кнопки до результата.
5. Локальный `whisper.cpp`, сравнить с API.

Целевая задержка: **меньше секунды** от отпускания кнопки. Для команд — жёстче,
там задержка ощущается как «не сработало», и человек жмёт второй раз.
